# Dieta Fácil no PostgreSQL

Consulte o [catálogo de erros das procedures](../ERROS.md).

O schema `dieta_facil` preserva as 15 tabelas e os relacionamentos do DER. Pode ser instalado em PostgreSQL local, em homologação ou em um serviço gerenciado. Use o DDL como primeira migração versionada do backend.

## Executar em um banco de testes

No PowerShell, a partir desta pasta, com o cliente `psql` e um banco vazio chamado `dieta_facil_teste` em um servidor local:

```powershell
psql -X -h localhost -U postgres -d dieta_facil_teste -v ON_ERROR_STOP=1 --single-transaction -f 01_ddl_estrutura.sql -f 02_dml_carga_inicial.sql
```

O usuário da execução precisa poder criar o schema. O banco de testes deve existir antes do comando. Para instalar a estrutura em outro ambiente, execute somente o arquivo 01 com a conexão e o papel de migração desse ambiente. O arquivo 02 contém dados exclusivamente fictícios e ajusta as sequências dos IDs que carrega.

## Diferenças em relação ao SQLite

- IDs gerados usam `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Chaves compartilhadas e estrangeiras usam `BIGINT`.
- Nascimento usa `DATE`. Instantes de registro, mensagem e consulta usam `TIMESTAMPTZ`. A data civil dos relatórios precisa de um fuso definido.
- As medidas nutricionais usam `NUMERIC`. Os índices de unicidade de conta usam `lower`. A busca exata de catálogo deve usar `WHERE lower(nome) = lower($1)` para usar o índice correspondente.
- O DER anterior continua descrevendo as relações. Os tipos mostrados nele são da versão SQLite. Planos medidos no SQLite precisam ser reproduzidos no PostgreSQL para a defesa.

## Reaproveitamento no banco online

O backend Kotlin pode se conectar ao PostgreSQL e expor uma API para o aplicativo. O candidato a armazenamento offline é o SQLite local. Antes de permitir escrita offline, defina quais entidades sincronizam, quem gera os IDs, como propagar exclusões e como resolver conflitos. Essas decisões podem gerar novas migrações.

Antes de usar dados reais, defina as permissões da API para pacientes e nutricionistas, a política de retenção dos dados biométricos e o processo de backup e restauração. Mantenha credenciais do banco no backend e use um papel de execução com permissões restritas, separado do papel de migração.

Os cenários transacionais e os planos estão no [script 04](04_testes_e_transacoes.sql).

## Exclusão definitiva de refeição registrada

Instale o arquivo 03 com `psql -v ON_ERROR_STOP=1 --single-transaction -f 03_programacao_avancada.sql` usando o papel de migração. A instalação em uma transação publica a procedure e a restrição de execução juntas. Conceda `USAGE` no schema e `EXECUTE` na procedure apenas ao papel do backend autorizado. Mantenha o acesso direto de exclusão às tabelas restrito.

O backend deve preencher o primeiro argumento com o ID da sessão autenticada. O segundo argumento é o ID da refeição. O terceiro é o parâmetro de saída e recebe `NULL` na chamada, por exemplo `CALL dieta_facil.excluir_refeicao_registrada(1, 1, NULL);`. A procedure recusa refeições de outro usuário e refeições sem registro. Em caso de sucesso, retorna o ID do registro removido. O registro, a refeição e seus itens são removidos na mesma operação. Os alimentos do catálogo são preservados.


## Registro definitivo de refeição

A procedure `dieta_facil.registrar_refeicao_completa` aceita no mínimo um lançamento. Cria uma refeição avulsa, registra a data informada no diário e grava cada quantidade na unidade-base do alimento. Dois lançamentos do mesmo alimento são preservados. O backend passa o ID da sessão autenticada e pode usar apenas alimentos compartilhados ou do próprio usuário. Se qualquer item falhar, o PostgreSQL desfaz as gravações da chamada.

```sql
CALL dieta_facil.registrar_refeicao_completa(
    1, 'Almoço', TIMESTAMPTZ '2026-11-25 12:30:00-03',
    '[{"alimento_id": 1, "quantidade": 100}, {"alimento_id": 1, "quantidade": 50}]'::jsonb,
    NULL
);
```

A saída é `registro_criado_id`. Conceda `EXECUTE` nessa procedure apenas ao papel autorizado do backend. A regra de mínimo é aplicada ao registrar pela procedure. Os gatilhos de integridade também protegem o mínimo em alterações posteriores.

Os testes confirmaram rejeição de lista vazia e de alimento inexistente, rollback após a falha do segundo item, preservação de duas entradas do mesmo alimento e exclusão definitiva somente pelo dono. ## Edição de refeição registrada e histórico

`dieta_facil.alterar_refeicao_registrada` recebe o usuário autenticado, o ID da refeição, o nome, a data/hora do diário e a lista final de lançamentos. Envie o `id` para manter ou editar um lançamento existente. Omita o campo para criar um lançamento. Lançamentos existentes omitidos da lista são removidos. A lista final precisa ter pelo menos um alimento. A saída é `registro_alterado_id`.

Neste exemplo, o lançamento 123 precisa pertencer à refeição 45:

```sql
CALL dieta_facil.alterar_refeicao_registrada(
    1, 45, 'Jantar', TIMESTAMPTZ '2026-11-25 20:00:00-03',
    '[{"id": 123, "alimento_id": 1, "quantidade": 120}, {"alimento_id": 1, "quantidade": 70}]'::jsonb,
    NULL
);
```

Quando há alteração efetiva, `historico_refeicao` guarda o ID do registro, o ID da refeição, o autor, o instante da edição e os estados anterior e posterior. Os estados incluem nome, data do diário em UTC e lançamentos. O histórico é gravado na mesma operação e sobrevive à exclusão da refeição. A política de retenção do histórico para produção ainda precisa ser definida.

Use a procedure como via de edição do backend e conceda `EXECUTE` apenas ao papel autorizado. Atualizações diretas nas tabelas passam fora da auditoria desta procedure. A validação das alterações e a gravação do histórico foram testadas no PGlite, incluindo rejeição de outro usuário, lista vazia, rollback após erro em um lançamento, chamada idêntica e preservação do histórico após a exclusão.

## Views de consumo e agenda

As duas views são instaladas pelo script 03 e estão disponíveis também no SQLite de demonstração.

- `vw_consumo_diario` consolida refeições e lançamentos por usuário e dia UTC. A soma usa quantidade × kcal por 100 unidades ÷ 100. Lançamentos repetidos contam separadamente. O `HAVING` exige ao menos um lançamento no dia. A view compara o total com a meta vigente, com estados `acima_da_meta`, `dentro_da_meta` e `sem_meta`. Alterar a meta vigente ou o valor nutricional do catálogo afeta relatórios anteriores.
- `vw_agenda_consultas` reúne paciente, nutricionista, horário de início e fim e status, inclusive consultas canceladas. O consumidor pode filtrar por status e ordenar pelo início.

Exemplos para PostgreSQL:

```sql
SELECT * FROM dieta_facil.vw_consumo_diario
WHERE comum_id = 1 ORDER BY dia DESC;

SELECT * FROM dieta_facil.vw_agenda_consultas
WHERE nutricionista_id = 21 ORDER BY inicio_em;
```

No SQLite, use os nomes sem o prefixo `dieta_facil.`. No backend, aplique os filtros de autorização do usuário autenticado antes de expor dados. As views abrangem todos os registros a que o papel de banco tem acesso conforme suas permissões.

## Funções de calorias e meta

- `calcular_calorias_lancamento(quantidade, kcal_por_100)` retorna kcal da porção. Quantidade e referência nutricional devem usar a mesma unidade-base, g ou ml. A função preserva as casas decimais antes da soma. A view PostgreSQL reutiliza a função, e a view SQLite usa a mesma expressão em SQL.
- `calcular_meta_calorica(sexo, idade, altura_cm, peso_kg, nivel_atividade)` calcula a meta pela fórmula revisada de Harris-Benedict que o app já usa. Aceita os códigos `M` e `F`, idade em anos, altura em cm, peso em kg e `SEDENTARIO`, `LEVE`, `MODERADO` ou `MUITO_ATIVO`. Retorna kcal/dia arredondadas para inteiro positivo. A função só calcula. O fluxo de escolha e gravação da meta continua separado. No app local, o cálculo em Kotlin continua disponível sem depender do PostgreSQL.

As funções centralizam os cálculos para consultas e relatórios do banco online. O cálculo da meta permanece no app para funcionamento offline. As entradas inválidas retornam os códigos `P1010` a `P1012`, descritos no [catálogo de erros](../ERROS.md).

```sql
SELECT dieta_facil.calcular_calorias_lancamento(150, 130);
SELECT dieta_facil.calcular_meta_calorica('F', 29, 164, 62, 'LEVE');
```

## Gatilhos de auditoria e integridade

- `trg_auditar_exclusao_refeicao` salva no histórico o último estado da refeição antes da exclusão do registro, incluindo nome, data e itens. O evento tem ação `exclusao` e estado posterior nulo. O autor é o dono cuja identidade o backend autenticou antes de chamar a procedure. O histórico da edição continua sendo gravado pela procedure de edição, uma vez por mudança efetiva, com ação `alteracao`. Se a exclusão for desfeita, seu evento também é desfeito.
- Os gatilhos de integridade verificam a criação ou troca de uma refeição do diário e a remoção ou transferência de seus itens. No PostgreSQL, a regra é verificada no fim da transação. Isso permite criar ou substituir itens dentro da mesma operação. Uma refeição registrada vazia resulta em `P1013`. Os rascunhos sem registro podem ficar vazios.
- No SQLite da entrega, os gatilhos são imediatos. Para registrar, grave a refeição e seus itens antes do registro. Para substituir o único item, adicione o novo antes de remover o anterior. Para excluir definitivamente, apague o registro do diário antes da refeição, na mesma transação. A exclusão também gera histórico no SQLite. Esse arquivo de demonstração é separado do banco SQLDelight do app. O SQLite precisa incluir as funções JSON.
- O acesso direto de escrita às tabelas deve ficar restrito para assegurar que o autor registrado seja o dono autenticado. O evento de exclusão preserva dados de alimentação no histórico. Defina a retenção antes do uso em produção.

Testados em PGlite e SQLite: registro vazio, remoção ou transferência do último item, exclusão com histórico e rollback. No PGlite, também foi testada a substituição do único item dentro de uma chamada.

## Testes e transações

Depois de instalar os scripts 01 a 03 e a carga fictícia, execute o [script 04](04_testes_e_transacoes.sql) em uma conexão de teste:

```powershell
psql -X -h localhost -U postgres -d dieta_facil_teste -v ON_ERROR_STOP=1 -f 04_testes_e_transacoes.sql
```

O script usa `BEGIN`, `COMMIT` e `ROLLBACK`. Execute-o separadamente, pois ele abre e encerra as próprias transações. Os blocos PL/pgSQL com `EXCEPTION` usam subtransações. Quando ocorre a falha esperada, o PostgreSQL desfaz as operações do bloco antes de executar o tratamento.

1. **Último lançamento.** Registra uma refeição com um alimento, tenta removê-lo e obtém `P1013`. Verifica que o item voltou após a falha e que uma edição válida preserva os dois lançamentos e grava o histórico. O rollback externo remove os dados temporários.
2. **Exclusão e histórico.** A tentativa por outro usuário é rejeitada com `P1001`. A exclusão pelo dono remove a refeição e grava o evento. Uma falha simulada depois da exclusão reverte os dois efeitos. O teste verifica a restauração do registro e dos itens e confirma que a auditoria voltou à contagem inicial.

O script também executa exemplos das duas funções e das duas views. Ele foi executado depois de 01 a 03 no PGlite. Uma comparação antes e depois confirmou que as linhas do diário, das refeições, dos lançamentos e do histórico foram preservadas. Sequências de IDs podem avançar durante os testes, mesmo com rollback.

### Planos de execução observados

Na carga de demonstração do PGlite, as seis consultas do script usaram `Bitmap Index Scan` com os índices abaixo, sem forçar a escolha do otimizador. Alguns planos incluíram uma ordenação adicional. Os seis índices também foram observados no PostgreSQL 18.7 nativo para Windows. Consulte o [resultado do script 04](evidencias-postgresql-18.7.txt). Volume de dados, estatísticas e versão podem mudar a decisão do otimizador.

| Alimentos pelo nome, sem distinguir maiúsculas | `idx_alimento_nome` |

| Mensagens por usuário | `idx_mensagem_comum_data` |
